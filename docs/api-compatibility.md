# API 호환성 규칙 (앱 구버전 대응)

웹은 배포하면 모두가 바로 새 코드를 쓰지만, 앱은 예전 빌드가 사용자 폰에 남는다.
OTA(expo-updates)는 JS 만 바꾸고, 다음 실행 때, 같은 런타임 빌드에만 적용된다.
그래서 서버 응답·요청 계약은 **이미 배포된 앱 빌드가 깨지지 않게** 바꾼다.

## 그냥 해도 되는 변경

- 응답에 필드 추가
- 엔드포인트 추가
- 요청에 **선택** 필드 추가 (서버 Jackson 은 모르는 필드를 무시한다)

## 앱을 깨는 변경 (아래 절차를 따른다)

- 응답 필드 삭제·이름 변경·타입 변경
- 응답 필드를 non-null → nullable 로 바꾸기
- 요청 필드를 선택 → 필수로 바꾸기
- 같은 필드의 의미 변경 (예: 부분 수정 → 전체 교체. #767 의 구독 API 는 `organizationIds` 를 안 보내면 학교 구독이 지워진다)
- 응답 enum 에 새 값 추가 (앱이 모르는 값을 받는다. 앱은 `default` 로 처리하게 짜되, 서버도 깨지는 변경으로 본다)

## 깨는 변경 절차 (expand → contract)

1. **expand**: 옛 필드·동작을 그대로 둔 채 새 필드·동작을 추가한다.
2. 앱이 새 필드를 쓰도록 배포한다 (JS 만이면 OTA, 아니면 새 빌드).
3. 옛 빌드가 얼마나 남았는지 본다.
   - Prometheus: `app_client_requests_total{platform, build}`
   - 로그(JSON): 요청마다 `APP_PLATFORM`·`APP_VERSION`·`APP_BUILD`
4. 남은 옛 빌드를 끊어야 하면 최소 지원 빌드를 올린다.
   - be-config `app.version.{ios|android}.minimum-build` (기본 0 = 강제 없음), 배포 필요
   - `store-url` 도 같이 넣는다. 비어 있으면 업데이트 화면에 버튼이 없어 사용자가 할 수 있는 게 없다
   - 그보다 낮은 빌드는 `GET /app/versions` 를 보고 업데이트 화면에서 멈춘다
5. **contract**: 옛 빌드가 사라진 뒤 옛 필드·동작을 지운다.

## URL 버전 (`/v2/...`)

위 절차로 피할 수 없는 변경일 때만, **그 엔드포인트에만** 붙인다. 전체 `/v1` 도입은 하지 않는다.
웹·매니저 데스크톱·앱이 전부 경로를 바꿔야 해서 비용이 크다.

## 앱이 보내는 헤더

| 헤더 | 예 | 비고 |
|------|----|------|
| `X-App-Platform` | `ios` | `ios` / `android` |
| `X-App-Version` | `0.1.0` | 네이티브 앱 버전 |
| `X-App-Build` | `5` | 네이티브 빌드 번호 (OTA 와 무관) |

웹은 보내지 않는다. 값이 이상하면 서버는 무시한다.
